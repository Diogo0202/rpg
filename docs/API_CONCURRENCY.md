# Limite global de requisições simultâneas

`SharedAdmissionMiddleware` fornece um limite global de dez requisições para `/api/v1`. Em modo `process`, ele delega ao `ConcurrencyGate` já existente em `ApiSecurityMiddleware`; esse limite cobre apenas um processo. Em modo `supabase`, cada requisição recebe um UUID gerado pelo servidor, adquire uma das dez vagas no RPC e a libera em `finally`.

Para ativar a coordenação compartilhada, defina `API_CONCURRENCY_BACKEND=supabase`, `SUPABASE_URL` e `SUPABASE_SERVICE_ROLE_KEY` e aplique a migration `20261018130000_api_concurrency.sql`. O app já registra os middlewares nesta ordem de execução: CORS, auditoria, admissão compartilhada, segurança local e rotas. Os 60 segundos incluem autenticação, leitura do corpo e envio da resposta. Health e preflight permanecem disponíveis quando todas as vagas estão ocupadas.

Se `API_CONCURRENCY_BACKEND` não estiver definido, Vercel, AWS Lambda, Cloud Run (`K_SERVICE`) e `WEB_CONCURRENCY` acima de 1 escolhem `supabase`; os demais ambientes escolhem `process`. Um modo `process` explícito em runtime distribuído falha fechado com 503. Também há 503 se o modo Supabase estiver sem configuração, se o RPC falhar, ou se a aquisição expirar. Não há fallback em memória nesse modo. A vaga ocupada retorna 429 com `Retry-After: 1`; a aplicação não é chamada.

O banco mantém dez linhas fixas, cada uma com token e expiração opcionais. O RPC seleciona uma linha livre ou vencida com `FOR UPDATE SKIP LOCKED`, depois grava o UUID e vence o lease 120 segundos depois segundo `clock_timestamp()` do PostgreSQL. Aquisição não espera por locks. Se a vaga final estiver sendo escrita em outra transação no mesmo instante, uma chamada concorrente pode receber 429 conservador porque `SKIP LOCKED` não aguarda essa linha. O RPC de liberação limpa a linha que contém exatamente o token recebido. O timeout HTTP para adquirir é de 3 segundos. O orçamento da aplicação é de 60 segundos e inclui o tempo de autenticação, corpo e resposta. A liberação também tem timeout de 3 segundos e falhas geram apenas um log genérico, sem tokens nem detalhes da exceção.

Um timeout antes do início da resposta produz HTTP 504. Se os headers já começaram, o middleware relança o timeout para o servidor encerrar a resposta sem enviar um segundo conjunto de headers. Cancelamentos e exceções tentam liberar a vaga. Se o processo morrer de forma abrupta ou a tarefa for terminada sem executar `finally`, o lease pode ocupar uma vaga até expirar, por no máximo 120 segundos. O limite evita excesso de admissão, mas não garante que todo pedido consiga vaga durante falha do coordenador.

A migration cria e semeia dez linhas fixas, restringe execução dos RPCs a `service_role`, habilita RLS na tabela privada, não concede políticas aos clientes e revoga o acesso direto. O `service_role` deve permanecer somente na configuração privada do servidor. A migration foi verificada estaticamente; não foi executada contra um PostgreSQL nesta tarefa.

Outros runtimes com múltiplos processos também precisam de `API_CONCURRENCY_BACKEND=supabase`, mesmo quando não expõem as variáveis detectadas. Por exemplo, `uvicorn --workers 2` não define necessariamente `WEB_CONCURRENCY`. Todos os processos devem apontar para o mesmo projeto Supabase.

O orçamento usa cancelamento assíncrono. Python não encerra automaticamente trabalho síncrono que já está rodando em uma thread. Para manter o teto de execução diante de operações que ignoram cancelamento, o servidor deve encerrar a função antes do vencimento de 120 segundos do lease. Novos provedores de IA e tarefas pesadas precisam de timeouts próprios menores que o orçamento de 60 segundos. Os testes com coordenador falso comprovam a admissão entre duas instâncias; a atomicidade das linhas, os grants e a limpeza de leases vencidos ainda dependem da execução dos testes pgTAP no PostgreSQL.
